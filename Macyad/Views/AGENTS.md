# Views

## Purpose
SwiftUI-вьюхи приложения MacYaD, принадлежащие таргету `Macyad` (app). Каталог разбит на пять фичевых подкаталогов. Views обязаны общаться с бизнес-логикой только через ViewModels или `AppModel`; прямые вызовы Infrastructure-слоя (rclone, файловая система, процессы) из Views запрещены. Вся AppKit-интеграция проходит через `PlatformAdapters/`.

## Subdirectories
| Directory | Purpose |
|-----------|---------|
| Activity | Журнал операций синхронизации и UI ревью проблемных файлов |
| Onboarding | Пошаговый онбординг: установка rclone и настройка remote |
| Pairs | Список sync-пар, детали пары и создание/редактирование |
| Settings | Настройки приложения: аккаунты Yandex, уведомления, язык, запуск при логине |
| Shell | Основная навигационная оболочка окна и компактный menu bar popover |

## For AI Agents

### Working In This Directory
- Все новые вьюхи пишутся на SwiftUI; AppKit-код инкапсулируется в `PlatformAdapters/` и передаётся в Views через замыкания или `@EnvironmentObject`.
- Не создавай файлы прямо в `Views/` — размещай в нужном фичевом подкаталоге.
- Строки UI берутся из `appModel.copy` (`AppCopy`); не хардкодь пользовательский текст.
- Действия именуются строго: "Push to Yandex", "Pull from Yandex", "Check Yandex". Одна операция — одно название, без конкурирующих вариантов вроде просто "Pull".

## Design Principles

Раньше жили отдельным `DESIGN_PRINCIPLES.md` в корне; перенесены сюда, потому что это рабочие правила для того, кто правит вьюхи, а не публичный документ.

### Позиционирование

MacYaD должен ощущаться как профессиональный системный инструмент, а не как web-дашборд или растянутая мобильная оболочка.

Оптимизируем под: скорость, ясность, keyboard-first работу, плотность информации, быстрое считывание состояния, низкий визуальный шум, предсказуемое поведение окна, Dock и menu bar.

Не оптимизируем под: маркетинговую подачу, крупные touch-таргеты, большие пустые отступы как самоцель, onboarding-heavy сценарии, привычность web-дашборда.

Качество сверяем с Xcode, TablePlus, Raycast, Nova, Panic Transmit, Tailscale, VMware Fusion. Если новый экран не смотрится в этом ряду — решение дрейфует не туда.

### Граница SwiftUI и AppKit

SwiftUI — основной слой. AppKit допустим только как узкий явный мост для того, что SwiftUI не моделирует надёжно: menu bar / `NSStatusItem`, жизненный цикл `NSWindow` и activation policy, file/folder pickers, responder chain и прочие края системной интеграции. Переносить целые экраны в AppKit без явной причины нельзя.

### Раскладка и плотность

Базовая форма — sidebar + content + inspector. Предпочитать split views, resizable-колонки, компактные тулбары, inline-действия рядом с выбранной сущностью, вторичные детали в inspector или `sheet`.

Избегать: одноколоночной мобильной композиции на широком окне, гигантских hero-секций, дашбордов из карточек как основной раскладки, фиксированных коротких блоков там, где данные должны занимать доступную высоту.

Интерфейс плотный, но читаемый: усиливать иерархию раньше, чем добавлять воздух; держать компактные высоты строк; использовать стандартную типографику macOS вместо раздутых заголовков; уменьшать padding раньше, чем добавлять ещё один контейнер.

### Поведение оболочки

- Иконки в menu bar и Dock согласованы и не мигают разными глифами при launch, reopen, close, quit.
- Первый foreground-запуск открывает главное окно осознанно и без лишнего мерцания.
- Фоновая плановая или ручная активность не вытаскивает окно на передний план сама.
- Красная кнопка закрытия прячет окно, но не завершает menu bar utility; выход — только явной командой.
- Никаких неожиданных permission prompt'ов до явного намерения пользователя, если этого можно избежать архитектурно.

### Представление данных

- Для операционных данных — строки, списки и панели, а не декоративные карточки.
- Статус держать рядом с сущностью, к которой он относится.
- Моноширинный текст для путей, команд, timestamp и логов `rclone`, когда это помогает чтению.
- Событие журнала хранит минимум severity, timestamp, краткое summary и подробности; warning и alarm сохраняют полный stderr/лог `rclone`, когда он доступен.
- Причина warning или error должна открываться из UI в один клик — без ручного чтения внешнего лог-файла.

### Menu bar popover

Открывается мгновенно и остаётся компактным: сразу actionable-экран, одна очевидная группа быстрых действий для активной пары, короткий блок недавней активности, сгруппированные компактные секции. Избегать: раздутых popover'ов, глубоких стеков навигации, длинных скроллящихся экранов.

### Антипаттерны

Не отправлять в продукт интерфейсы, похожие на generic SaaS admin template, Notion-подобный холст из карточек, Electron-дашборд с гигантскими отступами, планшетный UI, растянутый до десктопа, декоративный градиент как структурную основу раскладки. Плюс: focus stealing во время фоновых действий, рассогласованное поведение Dock и menu bar, состояние, где warning или error есть, а причина из UI не видна.

### Чек-лист перед принятием UI-изменения

- Это ощущается как нативное macOS-приложение, а не web-first оболочка?
- Достаточно ли информации видно сразу, без лишнего скролла?
- Не стоит ли заменить карточки на строки, панели или inspector?
- Быстрые действия рядом с выбранной парой?
- Можно ли открыть warning или error и увидеть полные детали и лог?
- Предсказуемо ли ведут себя launch, close, reopen, Dock и menu bar?
- Удобно ли это тому, кто работает с клавиатуры?

### Testing Requirements
Ручное тестирование через `./script/build_and_run.sh`. Автоматизированные UI-тесты — `MacyadUITests/`. Логика ViewModels покрывается unit-тестами в `MacyadTests/`.

### Common Patterns
- `@EnvironmentObject var appModel: AppModel` — основной источник данных во всех Views.
- `@EnvironmentObject var environment: AppEnvironment` — доступ к окружению (сервисы, зависимости).
- `@ObservedObject var viewModel: XxxViewModel` — для фичевых ViewModel, где требуется.
- Листы (`sheet`) открываются через `@State private var isPresented` в родительской вьюхе.
- Inspector/detail-панели компонуются в `Shell/MainWindowView` через `NavigationSplitView`.
